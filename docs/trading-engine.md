# Demo trading engine(s) — reference for AI agents working on this system

This doc exists so any AI (Claude, Codex, a fresh session with no prior context) can pick up work on the demo trading system without re-deriving history from scratch. Keep it updated: when you change something material, add a dated entry to **Version history**; when you find something worth trying but don't build it, add it to **Ideas / future work** instead of losing it in a chat transcript.

There are **two independent trading systems** sharing this codebase. They do not share code, state, locks, or settings keys. Do not assume a change to one affects the other.

| | Council engine | Grid paper engine |
|---|---|---|
| Mechanism | 5-strategy momentum/reversal council vote + guardian risk layer | Standing ladder of buy/sell orders across a price range |
| Status | **Live on `testnet_execute`** — real testnet orders, demo funds only | **Live paper-only** — simulated fills, zero real orders |
| Core file | `src/server/demo-trading-engine.ts` | `src/server/grid-paper-engine.ts` |
| API | `src/routes/api/demo-trading.ts` | `src/routes/api/demo-trading-grid.ts` |
| Config lives at | `settings.demoTrading` | `settings.demoTradingGrid` |
| Config API action | `set_demo_config` (in `src/routes/api/finance.ts`) | `set_grid_config` (in `src/routes/api/finance.ts`) |
| Finance-store kinds | `demo_strategy_score`, `demo_open_position`, `demo_trade_log`, `demo_guardian_block`, `paper_shadow_decision`, `learning_candidate` | `demo_grid_state`, `demo_grid_trade` |
| Cron (cycle) | `Demo Trading Cycle`, `*/5 * * * *` | `Demo Trading Grid Cycle`, `*/15 * * * *` |
| Cron (scoreboard) | `Demo Trading Scoreboard`, daily `5 20 * * *` | `Demo Trading Grid Scoreboard`, daily `0 20 * * *` |
| Offline backtest | `src/server/trading-backtest.ts` + `scripts/backtest-trading.ts` | `src/server/grid-backtest.ts` + `scripts/backtest-grid.ts` |

Both are gated behind `hermes-workspace.service`, a **systemd-managed production build** — `:3000` runs `server-entry.js` from `dist/`, not a dev server. Source edits do not take effect until `pnpm build && sudo systemctl restart hermes-workspace.service`. This is a consequential, gated action — see **Safety model** below.

## Architecture

### Council engine

- `src/server/trading-strategies.ts` — pure `Strategy` interface (`evaluate(candles) → {signal, confidence, reason}`), one directional signal per strategy per symbol per cycle. Five strategies: `sma_crossover`, `rsi_reversion`, `macd_momentum`, `breakout`, `trend_pullback`. `councilVote()` combines them weighted by accumulated per-strategy score. Per-strategy scoring (`applyTradeOutcome`) folds realized PnL into a running score/win-rate with loss-streak cooldown.
- `src/server/trading-guardian.ts` — pre-order risk layer: position cap, per-trade quote cap, daily/weekly loss halt, open-drawdown halt, per-strategy loss-streak cooldown, balance floor. Exits are never gated, only entries.
- `src/server/demo-trading-engine.ts` — the cycle: council vote → guardian check → execute. Exit priority (highest to lowest): ATR stop → fixed stop-loss → ATR trailing → percent trailing → ATR target → fixed take-profit → owner-strategy SELL → council SELL → **max-hold expiry** (lowest priority — only fires if nothing else did). Execution modes: `paper` (simulated, `PaperBinanceClient`), `testnet` (`binance-demo-client.ts`, hard-locked to `demo-api.binance.com`), `live` (gated separately, currently inactive). A module-level lock (`cycleInProgress`) serializes cycles — **do not** build new functionality that calls into this engine's internals expecting to run concurrently with it.
- Guardrails: `settings.tradingMode` (`paper_trade` / `testnet_execute` / `live_*`) and `settings.emergencyKillSwitch` (independent master cutoff, decoupled from mode) both gate execution. Disarming the kill switch requires the literal confirmation phrase `I_UNDERSTAND_DISABLE_SAFETY_CUTOFF`.

### Grid paper engine

- `src/server/grid-paper-engine.ts` — incremental, stateful. Persists per-symbol grid state (`demo_grid_state`: armed levels, held/unheld, range bounds, pause/halt flags, `lastProcessedOpenTime`) between cycles and only steps forward through candles newer than what was last processed — it does **not** replay from scratch each cycle, because that would silently reshuffle the armed range every time the fetch window moves. Fills are detected from candle high/low (not just close), sells settled before buys within the same bar. Own lock (`gridCycleInProgress`), independent of the council's.
- Deliberately reimplements the offline `grid-backtest.ts`'s per-candle rules rather than importing them — matches this repo's existing precedent of separate offline/live pairs (`trading-backtest.ts` vs. `demo-trading-engine.ts` don't share a core either).
- Reads public market data only (`fetchBinanceKlines` in `binance-market.service.ts`) — no API keys, no signed requests, no real orders possible even in principle.
- Only gate wired live: `efficiencyGate` (Kaufman's Efficiency Ratio). The range-width `chopGate` from the offline research exists in `grid-backtest.ts` but was deliberately **not** ported live — research showed combining the two gates hurt results.

### Offline research harnesses

- `src/server/trading-backtest.ts` — replays historical candles through the actual council/guardian code (`STRATEGIES`, `councilVote`, guardian checks) at candle-close fills. Supports train/test split (`splitCandlesByIndex`) and multi-fold walk-forward (`buildWalkForwardWindows`) — both exported and reused by the grid CLI too.
- `src/server/grid-backtest.ts` — standalone batch simulator for the grid mechanism (doesn't fit the `Strategy` interface — holds many concurrent partial positions, not one signal). Same fill/fee conventions as `trading-backtest.ts` for comparability.
- `scripts/backfill-candles.ts` — paginated Binance klines fetch → `~/.hermes/finance/candles-cache/{SYMBOL}-{interval}.json`. Use `--skip-store` for research-only symbols/intervals so the live finance store's candle cache (1000/symbol/interval cap) isn't touched.
- `scripts/backtest-trading.ts` / `scripts/backtest-grid.ts` — CLI runners. Both are **interval-agnostic** (`--interval` is a free parameter, not hardcoded) — confirmed via the 2026-07-09 scalping research, no code changes were needed to test 5m/15m.
- Reports saved to `~/.hermes/finance/backtest-reports/` (`backtest-...json` for council, `grid-...json` for grid — distinct prefixes, no collision).

## Safety model

- **Council** can place real testnet orders right now. Guardian + kill switch + trading-mode gate are the three independent layers; all three must permit an action.
- **Grid** cannot place real orders under any current code path — no execution client, no API keys, public-data-only. If a future session wires `testnet_execute` for the grid, that is a categorically new capability requiring its own explicit sign-off and its own execution-layer engineering (the grid holds many concurrent positions per symbol, which the guardian's one-position-per-symbol model doesn't support — do not try to reuse `trading-guardian.ts` as-is).
- **Deploying either engine's code changes requires `pnpm build && sudo systemctl restart hermes-workspace.service`.** This has repeatedly been treated as a gated action requiring explicit, specific user sign-off — a general "continue" earlier in a conversation has not been sufficient; ask again immediately before running it, naming the exact action.
- Never touch `~/.hermes/finance/finance.json` directly — always go through `readFinanceStore`/`writeFinanceStore` (`src/server/finance-store.ts`) so audit logging and the Postgres mirror stay consistent.

## How to extend

- **Add a council strategy**: implement the `Strategy` interface in `trading-strategies.ts`, add it to the `STRATEGIES` array, add a test in `trading-strategies.test.ts`. It's automatically picked up by both the live engine and `trading-backtest.ts`.
- **Add a grid config knob**: add the field to `GridEngineConfig`/`DEFAULT_GRID_ENGINE_CONFIG` in `grid-paper-engine.ts` (and the matching field in `grid-backtest.ts`'s `GridBacktestConfig` if it should be backtestable too — they are deliberately separate types, keep both in sync by hand), expose it in `set_grid_config` if it should be user-tunable.
- **Run a backtest**: `pnpm exec tsx scripts/backtest-trading.ts --help`-style flags are documented in each script's header docstring — read those first, they're kept current.
- **Test a new timeframe/symbol**: `scripts/backfill-candles.ts --skip-store` first, then just pass `--interval`/`--symbols` to either backtest CLI — no code changes needed for this class of research (confirmed 2026-07-09).
- **Register a new cron**: use `hermes cron create <cron-expr> --name "..." --script <name>.sh --no-agent --deliver telegram:2130622225`. **A bare duration like `'15m'` creates a one-shot job, not recurring** — always use an explicit cron expression (`'*/15 * * * *'`) and verify `schedule.kind === "cron"` (not `"once"`) in `~/.hermes/cron/jobs.json` after creating.

Next real lever: a volatility-spike/ATR-based secondary filter (distinct from both the range-width and efficiency-ratio gates already tried) that might catch whatever's different about that period.
- **Council regime/exit infrastructure exists but isn't fully wired.** `regimeSmaPeriod`, `trailingStopPct`, `maxHoldMinutes` are live (see version history) but `atrStopMultiple`/`atrTakeProfitMultiple`/`atrTrailingMultiple` and `enabledStrategies` are still coded in `EngineConfig` and validated in `trading-backtest.ts`'s CLI, but **not** exposed via `set_demo_config`. ## Closed — checked and rejected, do not re-research

Unlike the Ideas above, these were investigated and explicitly decided against. Don't spend time re-scoping them without a genuinely new reason.

- **Sharing one code path between backtest and live, driven by a virtual clock (from OctoBot, 2026-07-10).** OctoBot's backtester replays historical data through the *same* channel/producer/consumer pipeline live trading uses, via a `TimeManager` that fast-forwards a simulated clock. This conflicts with a deliberate choice already made in this codebase: `trading-backtest.ts`/`grid-backtest.ts` are intentionally separate reimplementations from `demo-trading-engine.ts`/`grid-paper-engine.ts` (see each file's own header comments) precisely so backtest research can't accidentally leak into or destabilize the live engine. Not revisiting this without a much stronger reason than "OctoBot does it this way" — the isolation was a deliberate tradeoff, not an oversight.
- **Binance stocks / bStocks (2026-07-09).** No public REST API found on `developers.binance.com` — appears to be an app/UI-only retail product (different regulatory category, securities not crypto). Not integrable via the standard `api.binance.com` key-based access this project uses. Re-check only if Binance publishes a dedicated stocks API.
- **Binance Simple Earn / flexible savings (2026-07-09).** Real, documented REST API exists (`/sapi/v1/simple-earn/flexible/list`), but confirmed **mainnet-only** by direct test (200 on `api.binance.com`, 404 on the testnet host `demo-api.binance.com` — no sandbox path exists for this product). Real yield checked live: USDT ~1.48% APY, USDC ~1.76% APY, ETH ~1.27% APY on the base flexible product — a "boosted" tier (e.g. 30%) exists but only on the first $200 subscribed, then drops to the base rate. **Rejected as not worth building**: it's real-money-only (no way to test/develop against testnet), the real spot account is reportedly unfunded, and the yield beyond the trivial promotional tier is savings-account-level, not worth the integration complexity (new client, new API surface, new "no sandbox" risk category). This is also conceptually different from everything else in this doc — treasury/idle-capital yield, not a trading strategy. **Naveen's explicit call: do not develop this into the engine, and do not look at it again.**
- **Market making (2026-07-09).** Mechanically distinct from the grid engine (dynamic bid/ask re-quoting around live mid-price with inventory-aware skewing, vs. the grid's static pre-computed levels) — but rejected on fee grounds, confirmed empirically, not just reasoned: queried our own testnet account's `GET /api/v3/account` directly and got `maker: 0.001, taker: 0.001` — identical 10bps for both, no maker rebate/discount of any kind. Market making is inherently higher-frequency and lower-margin-per-trade than even the 5m grid config that already got wiped out by this exact fee rate (see the shorter-timeframe research above) — there's no fee structure available to us that would let this survive. Re-check only if our account's commission structure changes (VIP tier, BNB discount enabled, etc.) — re-query `GET /api/v3/account` first, don't assume.
- **Leveraged/futures trading — scoped 2026-07-09, not built, don't re-scope from scratch.** Would need: a separate Binance Futures testnet account (`testnet.binancefuture.com`, Naveen must provision — cannot self-serve); a new execution client (`binance-demo-client.ts` is hard-locked to spot hosts by design, not extensible); a genuinely new risk layer (liquidation price depends on leverage + Binance's tiered maintenance-margin table, needs real-time margin monitoring, not the guardian's periodic checks — liquidation can happen intra-cycle); a funding-rate data feed if trading perpetuals specifically (nothing fetches this today — this is what the original "Arbitrage Bot" idea from the trading-bots page research was actually about, delta-neutral funding capture). Sizing: ~1.5–2x the grid paper engine build. **Verdict: not worth it on current evidence** — Round 10's offline short-research found no robust short alpha with the current strategies, and leverage amplifies an edge that isn't there rather than creating one. Only reconsider given a genuinely new signal or a specific funding-rate-arbitrage angle, not "add leverage to what we have."
